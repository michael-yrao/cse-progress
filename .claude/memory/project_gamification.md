## The design constraint that shapes everything: honest process only

The repo is explicitly anti-vanity — the tracker is "a work queue, not a trophy case," a
*shrinking* row count is healthy ([[project_library_carrying_capacity]]), and a dishonest 🟢 is
flagged ([[feedback_infer_comfort]]). So gamification here is **not** points-for-volume. Every
signal keys off a **genuine, unfakeable event**:

- a **graduation** 🎓 = three cold cleans across spaced intervals (cannot be rushed);
- a **retirement** 🏆 = a 🎓 clearing its spot checks;
- a **comeback** = a 🔴 later turned 🟢 on the same problem;
- a **study-day streak** = showing up.

**The failure to fear:** a badge or streak leaking into a rating (a soft 🟢 to keep a streak
alive). Mitigation is baked in — nothing rewards a raw count of easy greens or the rating itself,
and the streak survives a 🟡 (a rep happened). If a milestone ever tempts a soft call, the coach
says so.

## Why the streak is SR-honest, not a daily grind

Spaced repetition works by reviewing **when due**, not daily. A raw daily-grind streak would push
over-review and fight the effort budget, whose own rule is "never raise the ceiling to catch up"
([[feedback_midweek_reprice]], effort-budget reference). So the streak counts **study-days with a
rest-day allowance** (`gamification.streak_rest_day_allowance` in `cse.config.yml`) — consistency,
not grinding.

## Why "progress" = the pipeline, not row count

The truest "on track" signal for this system is problems **maturing up the ladder**
🔴→🟡→🟢→🎓→🏆 and the **trophy case** (🎓 + 🏆) growing — that is the accomplishment record. Row
count is still not progress. The four surfaced signals, in priority: study-day streak
(consistency), the maturation pipeline / trophy case (mastery), technique coverage (breadth),
on-schedule health (keeping up).

## Architecture — a decoupling contract

`scripts/gamify.py` (source tier — a tool that emits the value outranks a rule) reads records that
already exist (`dsa_progress.md`, `schedules/*.md`, `technique_coverage.md`) and emits
**`progress.json`**, a versioned, curated, public **data contract** (`progress.schema.json`) that
the site renders. Reuses `effort_budget.parse_rows` + the schedule regexes; `_console.force_utf8()`;
regenerated by `.githooks/pre-commit`; surfaced at session start by `session_start_memory.py`
(reads the JSON directly, fail-soft). Per-problem comfort timelines are reconstructed from the
schedules' End column; a rep predating the schedule archive degrades to an activity dot, never a
fabricated value. **Curated:** no solution code, no stuck-log prose — the public repo exposes
aggregate + status, not struggle notes.

A second, sibling contract (`learn-cheatsheet-contract-sep22`, `decisions.yml`) follows the same
source-tier/dashboard-tier split for `/learn`: `scripts/build_cheatsheets.py` reads the technique
docs + `intuition_cheatsheet.md` + `techniques.yml` and emits `dashboard/cheat-sheets.json` +
`dashboard/cheat-sheets.schema.json`, validated by `scripts/check_cheatsheets.py` — blocking in
pre-commit as of Sep 23, 2026, now that all 18 docs pass.

## Known limitations (recorded up front, so they don't surprise later)

- **Retirement retroactively shrinks the streak.** 🏆 Retired rows leave the tracker and take their
  `Rep Dates` with them, so `streak.longest` / `studyDays` (computed from the union of all rows' rep
  dates) will silently DROP the first time a problem retires (704 is first, ~Jan 22 2027). The streak
  is "days visible in the active library," not an immutable lifetime history. Acceptable for now; if it
  ever matters, the fix is to also read the `## 🏆 Retired` list's dates (they carry retirement +
  spot-check dates, not the full rep history — so it would be partial anyway).
- **Multi-variant timelines degrade to activity dots.** A number with >1 tracker row (21, 323, …)
  cannot have its per-rep comfort reconstructed (the schedule index is keyed by number, not method),
  so those rows show dots + a single anchored current-comfort point rather than a full curve. Honest
  by design — see `build_problems` in `gamify.py`.
- **`difficulty` is null for a 🆕 row.** Difficulty is joined from the TRACKER by lcNumber
  (`dsa_progress.md` has no difficulty column of its own to read); a 🆕 intake row hasn't earned a
  tracker row yet, so it honestly gets null rather than a guess. `startComfort` is null for the same
  reason on a 🆕/🎯-tagged row. `lcNumber`/`url` no longer null the same way (see
  `schedule-item-kind-tags-sep21`) — a bare-numbered 🆕 row's own `[LC]`/`[NC]` link now yields both.

**The lead idea (learner's):** the dashboard is an easy, high-value way to **show the user their
SCHEDULE** — "what do I do today / this week." For someone using cse-coach, "today's board + what's due"
is probably the single most valuable glance. Data already exists: `docs/foundations/schedules/<...>.md`
(the week's plan) + each row's `nextReview`. Would need a lightweight schedule slice in the
summary contract (today's / this-week's items — small), same summary-first discipline.

**Brainstorm — "what else offers a lot of value at a glance?" (candidates to weigh next session):**
- **Today's board / what's due today** ⭐ (the lead idea) — the day's problems + count, from the schedule + due dates.
- **Next up / one recommended action** — the single highest-value rep now (oldest overdue, or the active block).
- **On-track status headline** — one line: "on track" vs "behind" (overdue trend / this-week reps vs plan).
- **This-week ring** — reps or units done this week vs the effort-budget plan (floor/ceiling).
- **Upcoming reviews (next 7 days)** — a mini timeline of what's coming due.
- **Weakest spot** — the thinnest technique / the one closest to slipping — one nudge, not the whole list.

**Design principle for the redo:** landing = a handful of overview tiles (streak · today's board · on-track ·
this-week progress); everything else (pipeline breakdown, technique list, per-problem graphs) stays as
drill-downs. Keep the summary-first / lightweight rules. Plan it under the standing workflow
([[feedback-execution-workflow]]) when the learner returns to it.
